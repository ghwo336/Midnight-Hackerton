# ONCE Finance

**거래 내역을 공개하지 않으면서, 같은 매출채권으로 여러 금융사에서 중복 대출받는 것을 막는다.**

---

## 바로 실행하기: 지갑·faucet 불필요

클론하고 두 줄이면 데모가 뜬다. **지갑도, 테스트넷 자금도, Compact 툴체인도
필요 없다.** 컴파일된 회로와 증명키가 저장소에 들어 있다.

```bash
pnpm install
pnpm dev
```

→ **http://localhost:3040**

| | |
|---|---|
| 필요한 것 | Node 20+ , pnpm |
| 필요 없는 것 | 지갑, faucet, 테스트넷, proof server, Compact 컴파일러 |
| 걸리는 시간 | `pnpm install` 30초 내외, 기동 2초 |

포트는 API 3011 / 웹 3040이다. 이미 쓰는 포트가 있으면
`PORT=... pnpm --filter @once/api dev` 로 바꾼다.

### 데모 순서 (2분)

1. 왼쪽 **채권 #1** 클릭: 왼쪽에 파란 선이 생기면 선택된 것이다
2. **A에 신청**: 금융사 A에 파란 `지급 완료` 도장, 예치 잔액이 8천만 줄어든다
3. 채권 #1 다시 클릭 → **B에 신청**: 빨간 `이미 사용` 도장.
   **지급 금액 0**, 예치 잔액 그대로
4. 하단 **공개 원장** 확인: 컬럼이 중복확인값·금융사·금액·봉인값·블록·tx·시각뿐이다.
   채권 내용이 한 글자도 없다
5. **A1~A6** 버튼: 공격 시나리오가 전부 거부된다. **A5**가 클라이맥스다
   (한 채권에 두 금융사가 동시 신청 → 한쪽만 확정, 다른 쪽 자금 보존)

발표에서 손가락으로 가리킬 세 곳은 3번의 도장, 3번의 금액 `0`, 4번의 원장이다.

### 검증

```bash
pnpm test          # 50건: 불변식, 회로 라운드트립, 공격 A1~A9
pnpm test:attacks  # 공격 시나리오만
```

이 테스트들은 목 구현이 아니라 **컴파일된 Compact 회로를 실제로 실행한다.**
거부는 애플리케이션 계층이 아니라 회로의 `assert`가 만든 결과다.

거부 테스트는 "거부됐다"가 아니라 **"의도한 assert에서 거부됐다"**를 확인한다.
`.rejects.toThrow()`만 쓰다가 A3·A4가 오래 거짓 통과한 적이 있어서 바꿨다
([TEST_REPORT.md](docs/TEST_REPORT.md) §1).

### 로컬 모드가 무엇을 실행하는가

`packages/chain`의 시뮬레이터가 `contracts/managed/`의 컴파일된 회로를
Node에서 그대로 돌린다. 증명 생성·제출은 로컬에서 일어나고 네트워크를
타지 않는다. 회로 로직·assert·원장 상태 전이는 전부 진짜다.

로컬 실행이 대신하지 못하는 것은 노드의 증명 트랜스크립트 검증과 합의
계층의 트랜잭션 순서 결정이다. 그건 테스트넷 배포로 확인한다(아래).

## 1. 문제

납품업체가 대기업에 부품을 납품하고 다음 달에 1억 원을 받기로 돼 있다. 운영비가
급해서 이 받을 돈(매출채권)을 담보로 A캐피탈에서 8천만 원을 빌린다. 정상적인 금융이다.

그런데 같은 세금계산서를 B저축은행에도 들고 간다. B는 A가 이미 이 채권으로 대출해
줬다는 사실을 모른다. 서류는 진짜고 발급 기관도 확인된다. 그래서 B도 8천만 원을 내준다.

**1억짜리 채권 하나로 1억 6천만 원이 나갔다.** 국제상업회의소가 무역금융의 대표적
사기 유형으로 분류하는 수법이고, 기술이 필요 없다. PDF 하나를 두 군데 내면 된다.

### 왜 지금까지 안 막혔나

막는 방법은 뻔하다. A와 B가 "이 채권 이미 쓰였나요?"를 공유하면 된다.

그런데 그러려면 A가 B에게 누가 어떤 거래처와 얼마짜리 거래를 하는지를 넘겨야 한다.
그건 고객의 정보이자 A의 영업 정보다. 그래서 현실에서는 모두가 신뢰하는 중앙
운영자를 두는 방식으로 우회하고, 조회와 송금 사이의 틈은 여전히 열려 있다.

## 2. 왜 블록체인이고 왜 Midnight인가

### 블록체인인 이유: 조회가 아니라 원자 실행

기존 방식의 구멍은 여기다.

```
A: "아직 안 쓰인 담보네요." → 송금
B: "아직 안 쓰인 담보네요." → 송금
```

둘 다 확인은 정상적으로 마쳤다. **조회와 송금 사이에서 사고가 난다.** 그래서
중복 확인값 등록과 자금 지급이 쪼갤 수 없는 하나의 동작이어야 한다.

이 구현에서 그 한 동작은 `finance` 회로다. 같은 회로 안에서 nullifier를 삽입하고
자금을 보낸다. "조회 API를 만들고 각자 송금하게 하면 간단하다"는 제안은 제품을
없애는 제안이다.

### Midnight인 이유

블록체인까지는 정해졌다. 문제는 일반 공개 체인에 올리면 이렇게 된다는 것이다.

```
납품업체 / 구매기업 / 채권번호 / 1억 / 지급일 / 소유자
```

중복은 완벽하게 막히지만, 애초에 A가 B에게 못 넘기던 정보를 이제 아무나 보는 곳에
올린 셈이 된다. 문제를 푸는 방식이 문제를 재생산한다.

Midnight은 공개 상태와 비공개 상태를 한 계약 안에서 다룬다. 채권 원문은 보유자
쪽에 남고 원장에는 봉인값과 지문만 올라간다.

**과장하지 않는다.** 이더리움에 별도 ZK 스택을 붙여도 만들 수 있다. 차이는
가능·불가능이 아니라, 회로·계약·검증기가 한 언어 안에 모이며 공개 범위를
`disclose()` 호출 지점에서 코드로 감사할 수 있다는 점이다.

실제로 이 프로젝트에서 그게 작동했다. witness에서 유도된 값을 원장 연산에 넘기면
`disclose()` 없이는 **컴파일이 실패한다.** 비공개성이 규율이 아니라 컴파일 오류다.
`disclose()` 호출 19곳 전수 검토 결과는 [docs/TEST_REPORT.md](docs/TEST_REPORT.md) §3.2에 있다.

## 3. 공개되는 것 / 공개되지 않는 것

| 데이터 | 상태 |
|---|---|
| 채권 원문 (구매기업, 금액, 지급일, 계약) | **비공개**: 납품업체 보관 |
| 채권 고유번호, salt, 소유자 비밀키 | **비공개** |
| 봉인값 (commitment) | 공개: 내용 추론 불가 |
| 중복 확인값 (nullifier) | 공개: 같은 채권 재사용만 연결 |
| 발급자 Merkle 루트 | 공개 |
| 금융사 주소, 대출 금액 | 공개 |
| 심사용 상세 정보 | 납품업체 → 해당 금융사에만, 오프체인 |

프라이버시의 대상은 **다른 금융사와 일반 관찰자**다. 거래 중인 자기 대출기관에까지
정보를 숨기는 무담보 대출을 만드는 게 아니다. 심사하는 금융사는 필요한 정보를 본다.

### 핵심 불변식

```
INV-1  nullifier  = H("ONCE/nf", issuerId, invoiceId)
       → salt, 금융사, 시각, 신청자, 파일명에 의존하지 않는다

INV-2  commitment = H("ONCE/cm", invoiceId, faceAmount, ownerPk, salt)
       → salt를 포함한다

INV-3  nullifier 미사용 검사와 자금 지급은 같은 트랜잭션에서 일어난다
```

nullifier와 commitment의 **입력이 다르다**는 점이 설계의 핵심이다. 같은 채권을
salt만 바꿔 다시 봉인해도 nullifier가 같아서 거부된다.

## 4. 보장 범위와 한계

### 막는다
- 이 공유 컨트랙트를 쓰는 대출들 사이의 동일 채권 중복
- 동시 신청: 하나만 성공하고 나머지 자금은 보존
- 금액 위조, 소유권 위조, 입력 변조
- 미사용 시점에 만든 증명을 사용 후에 제출하는 것

### 막지 못한다
- 발급 기관이 허위 채권을 만들거나 같은 거래에 다른 번호를 두 번 발급하는 것
- 이 컨트랙트를 쓰지 않는 금융사에서 일어난 중복
- 구매 기업의 실제 상환, 법적 채권 집행
- 납품업체·금융사 단말 침해, 원문을 받은 금융사의 유출

### 인정하는 노출
완전한 익명을 주장하지 않는다. 어떤 채권이 금융됐다는 사실과 어느 금융사가 얼마를
취급했는지는 원장에 보인다. 중복을 감지하려면 최소한 그만큼은 필요하다.

추가로 두 가지를 기록해 둔다 ([자세히](docs/TEST_REPORT.md) §3.3).

- **대출 금액에서 액면금액이 추론된다.** 한도를 꽉 채워 빌리면
  `faceAmount = amount / LTV`가 드러난다.
- **리프 해시는 추측 확인을 허용한다.** 데모의 `invoiceId`는 32바이트 난수라
  문제없지만, 실사용 시 국세청 승인번호는 엔트로피가 낮다. 실제 제품이라면
  리프에 발급 기관만 아는 비밀값을 섞어야 한다.

### 데모 단순화: 반드시 읽을 것

실제 제품에서 채권 원문과 비밀키는 **납품업체 본인의 기기**에 있어야 한다.
이 구현에서는 데모 편의를 위해 NestJS가 역할별로 분리된 저장소에 보관한다.

분리는 논리적으로 강제된다. 모든 원문 조회가 `supplierId`를 요구하고,
`LenderController`는 `PrivateStateRepository`를 주입받지 않는다. 금융사 세션이
납품업체 원문에 닿는 경로가 코드에 존재하지 않는다. 그래도 서버가 원문을 들고
있다는 사실은 변하지 않는다. `PrivateStateRepository` 인터페이스 뒤에 두어
나중에 브라우저 저장소로 교체할 수 있게 했다.

**발급 기관은 신뢰한다.** 발급 기관이 허위 채권을 만드는 것은 이 제품이 풀지
않는 문제다. 다만 발급 기관을 **사칭**하는 것은 막는다 (A8).

| G5 프론트 | ✅ 3화면 + 공개 원장 + 공격 패널 |
| G6 검증 | ✅ A1~A9 전부 기대 결과, 테스트 50건 ([TEST_REPORT.md](docs/TEST_REPORT.md)) |

G4가 남아 있으므로 **배포 주소와 tx 해시가 아직 없다.** 대신 로컬 모드가
컴파일된 회로를 그대로 실행하므로, A1~A9의 거부는 애플리케이션 계층이
아니라 회로의 assert가 만든 결과다. 로컬 실행이 증명하지 못하는 것은
[SPIKE.md](docs/SPIKE.md) 마지막 절에 적어 두었다.

# 회로를 고쳤을 때만 필요하다. contracts/managed/ 가 저장소에 있으므로

## 7. 데모 시나리오

화면 세 개가 한 화면에 나란히 뜬다.

| 납품업체 | 금융사 A | 금융사 B |
|---|---|---|
| 비공개 채권 3건 보유 | 대출 제안 | 대출 제안 |
| A의 제안 수락 | 담보 확보 · **지급 완료** |: |
| 같은 채권으로 B에 신청 | 기존 대출 유지 | **중복 담보 · 지급 거부** |

이어서 공격 패널의 A1~A6을 차례로 누른다. 전부 거부되고 자금이 보존된다.

화면이 말 없이 증명해야 하는 세 가지:

| 주장 | 화면이 증명하는 방법 |
|---|---|
| 장부를 공유하지 않았다 | 금융사 B 패널과 공개 원장 어디에도 채권 내용이 없다 |
| 그런데 중복이 막혔다 | B의 도장이 `이미 사용`으로 찍힌다 |
| 자금이 나가지 않았다 | B의 금액이 `0`으로 남고 예치 잔액이 그대로다 |

> **장부는 안 보여줬는데, 사기는 막혔다.**

## 8. 구조

```
once/
├── contracts/src/once.compact     # finance 회로. INV-1/2/3이 여기서 성립한다
├── packages/
│   ├── domain/                    # 의존성 0. 순수 타입 + 규칙
│   ├── crypto/                    # 회로와 동일한 해시 (S1 라운드트립으로 강제)
│   └── chain/                     # 컴파일된 회로를 실행하는 시뮬레이터
├── apps/
│   ├── api/                       # NestJS. 포트/어댑터
│   └── web/                       # Next.js. 얇은 뷰
├── test/attacks/                  # A1~A9
└── docs/
```

의존 방향은 ESLint `no-restricted-imports`로 강제한다.

```
web  →  (HTTP)  →  api
api  →  application  →  domain
api  →  infrastructure  →  chain  →  Midnight SDK
domain  →  아무것도 의존하지 않음
```

체인 구현을 바꿀 때 `apps/api/src/app.module.ts`의 바인딩만 교체하면 되고
유스케이스는 수정하지 않는다.

## 9. 이 프로젝트가 아닌 것

- 실제 은행·전자세금계산서 API 연동
- 스테이블코인 또는 실제 자산 발행 (데모 자금은 컨트랙트가 발행한 토큰이다)
- KYC, 실명 인증, 신용 평가
- 대출 상환, 이자 계산, 연체 처리
- 채권 양도·유통 시장, NFT화
- 다중 발급 기관, 기관 간 거버넌스
- 분할 대출, 잔여 한도 관리
