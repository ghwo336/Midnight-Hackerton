# ONCE Finance: 제품 맥락

**읽는 순서: 이 문서 → `SPEC.md`**

이 문서는 구현 지시가 아니라 **판단 근거**다. 명세에 없는 상황을 만났을 때, 여기 적힌 목표와 경계에 비추어 결정한다. 명세와 충돌하면 `SPEC.md`가 우선한다.

---

## 1. 한 문장

거래 내역을 공개하지 않으면서, 같은 매출채권으로 여러 금융사에서 중복 대출받는 것을 막는다.

---

## 2. 막으려는 사기

납품업체가 대기업에 부품을 납품하고 다음 달에 1억 원을 받기로 돼 있다. 운영비가 급해서 이 **받을 돈(매출채권)**을 담보로 A캐피탈에서 8천만 원을 빌린다. 정상적인 금융이다.

그런데 같은 세금계산서를 B저축은행에도 들고 간다. B는 A가 이미 이 채권으로 대출해줬다는 사실을 모른다. 서류는 진짜고 발급 기관도 확인된다. 그래서 B도 8천만 원을 내준다.

**1억짜리 채권 하나로 1억 6천만 원이 나갔다.** 국제상업회의소가 무역금융의 대표적 사기 유형으로 분류하는 수법이고, 기술이 필요 없다. PDF 하나를 두 군데 내면 된다.

---

## 3. 왜 지금까지 안 막혔나

막는 방법은 뻔하다. A와 B가 "이 채권 이미 쓰였나요?"를 공유하면 된다.

그런데 그러려면 A가 B에게 **누가 어떤 거래처와 얼마짜리 거래를 하는지**를 넘겨야 한다. 이건 두 가지 이유로 불가능하다.

- **고객의 정보다.** 납품업체의 거래처와 매출 규모다.
- **A의 영업 정보다.** A의 고객 명단과 취급 조건이 경쟁사 B에게 통째로 넘어간다.

그래서 현실에서는 모두가 신뢰하는 중앙 운영자를 두는 방식(예: MonetaGo)으로 우회한다. 그 운영자를 믿어야 성립하고, 조회와 송금 사이의 틈은 여전히 열려 있다.

---

## 4. 이 제품의 핵심 주장: 구현이 지켜야 할 것

### 4.1 검증자에게 주는 답은 예 / 아니오 하나다

금융사 B가 알아야 하는 건 "이 담보 이미 쓰였나"뿐이다. 채권 내용도, 금액도, A의 장부도 필요 없고 받을 수도 없다.

> **구현 함의**: 공개 원장과 API 응답에 채권 원문 필드를 노출하는 코드 경로가 존재해서는 안 된다. 편의를 위해서라도 만들지 않는다.

### 4.2 프라이버시가 기능이 아니라 문제의 원인이다

채권 원문을 공개해도 되는 세상이었다면 이 사기는 애초에 없었다. A와 B가 엑셀을 주고받으면 끝이다. **못 보여주기 때문에** 이 문제가 존재하고, 그래서 못 보여주는 채로 검증하는 것 말고는 해결책이 없다.

> **구현 함의**: "일단 데이터를 다 올리고 나중에 가리자"는 접근은 이 제품의 부정이다. 처음부터 원문이 원장에 닿지 않는 경로로 설계한다.

### 4.3 조회가 아니라 원자 실행이다

기존 방식의 구멍은 여기다.

```
A: "아직 안 쓰인 담보네요." → 송금
B: "아직 안 쓰인 담보네요." → 송금
```

둘 다 확인은 정상적으로 마쳤다. 조회와 송금 사이에서 사고가 난다. 그래서 **중복 확인값 등록과 자금 지급이 쪼갤 수 없는 하나의 동작**이어야 한다.

> **구현 함의**: 이게 블록체인을 쓰는 이유 그 자체다. "조회 API를 만들고 각자 송금하게 하면 간단하다"는 최적화 제안이 나오면, 그건 제품을 없애는 제안이다. `SPEC.md`의 INV-3이 이 조항이다.

### 4.4 같은 채권이면 항상 같은 지문이 나와야 한다

파일명을 바꾸든, 다시 봉인하든, 다른 금융사에 내든, 같은 채권이면 같은 값이 나와야 중복이 잡힌다. 그래서 지문은 **발급 기관이 부여한 고유번호**에서 나와야 하고, 사용자가 바꿀 수 있는 값(salt, 파일 해시, 신청 시각)에 의존하면 안 된다.

한국에서는 전자세금계산서의 **국세청 승인번호**가 이 역할을 한다. 국세청이 부여하고, 거래마다 유일하고, 복사해도 바뀌지 않는다. 데모에서는 목업이지만 구조는 이걸 전제로 만든다.

> **구현 함의**: `SPEC.md`의 INV-1. 이걸 어기면 salt만 바꿔서 무한 재사용이 되고 제품이 통째로 무너진다.

## 5. 공개 / 비공개

| 데이터 | 상태 |
|---|---|
| 채권 원문 (구매기업, 금액, 지급일, 계약) | **비공개**: 납품업체 보관 |
| 채권 고유번호, salt, 소유자 비밀키 | **비공개** |
| 봉인값 (commitment) | 공개: 내용 추론 불가 |
| 중복 확인값 (nullifier) | 공개: 같은 채권 재사용만 연결 |
| 발급자 Merkle 루트 | 공개 |
| 금융사 주소, 대출 금액 | 공개 |
| 심사용 상세 정보 | 납품업체 → 해당 금융사에만, 오프체인 |

프라이버시의 대상은 **다른 금융사와 일반 관찰자**다. 거래 중인 자기 대출기관에까지 정보를 숨기는 무담보 대출을 만드는 게 아니다. 심사하는 금융사는 필요한 정보를 본다.

## 6. 보장 범위

### 막는다
- 이 공유 컨트랙트를 쓰는 대출들 사이의 동일 채권 중복
- 동시 신청: 하나만 성공하고 나머지 자금은 보존
- 금액 위조, 소유권 위조, 입력 변조
- 미사용 시점에 만든 증명을 사용 후에 제출하는 것

### 막지 못한다 (기능으로 만들려 하지 말 것)
- 발급 기관이 허위 채권을 만들거나 같은 거래에 다른 번호를 두 번 발급하는 것
- 이 컨트랙트를 쓰지 않는 금융사에서 일어난 중복
- 구매 기업의 실제 상환, 법적 채권 집행
- 납품업체 또는 금융사 단말이 침해당하는 것, 원문을 받은 금융사가 유출하는 것

### 인정하는 노출
완전한 익명을 주장하지 않는다. 어떤 채권이 금융됐다는 사실과 어느 금융사가 얼마를 취급했는지는 원장에 보인다. 중복을 감지하려면 최소한 그만큼은 필요하다.

> **구현 함의**: 이 경계를 넓히는 기능을 스스로 추가하지 않는다. 범위 밖 문제를 풀려고 아키텍처를 복잡하게 만들면 완성도가 떨어진다. README에 이 표를 그대로 싣는다.

## 7. 데모에서 보여줄 장면

우선순위 판단의 기준이다. **이 장면에 기여하지 않는 기능은 후순위다.**

화면 세 개를 나란히 띄운다.

| 납품업체 | 금융사 A | 금융사 B |
|---|---|---|
| 비공개 채권 3건 보유 | 대출 제안 | 대출 제안 |
| A의 제안 수락 | 담보 확보 · **지급 성공** |: |
| 같은 채권으로 B에 신청 | 기존 대출 유지 | **중복 담보 · 지급 거부** |

이어서 속이는 시도를 차례로 한다. 파일명 변경, 새 salt로 재봉인, 금액 부풀리기, 타인 채권, 동시 신청. 전부 거부되고 자금이 보존된다.

마지막 한 문장으로 끝낸다.

> **장부는 안 보여줬는데, 사기는 막혔다.**

이 문장이 화면으로 증명되려면, 공개 원장 패널에 채권 내용이 **한 글자도** 없어야 한다. 그래서 §4.1의 구현 함의가 데모의 성패를 가른다.

## 8. 이 프로젝트가 아닌 것

에이전트가 범위를 넓히기 쉬운 지점들이다. 전부 하지 않는다.

- 실제 은행·전자세금계산서 API 연동
- 스테이블코인 또는 실제 자산 발행
- KYC, 실명 인증, 신용 평가
- 대출 상환, 이자 계산, 연체 처리
- 채권 양도·유통 시장, NFT화
- 다중 발급 기관, 기관 간 거버넌스
- 분할 대출, 잔여 한도 관리

데모에 필요한 최소 구성은 **발급 기관 1곳, 납품업체 1곳, 금융사 2곳, 채권 3건**이다.

## 9. 왜 Midnight인가

블록체인까지는 §4.3에서 정해졌다. 문제는 일반 공개 체인에 올리면 이렇게 된다는 것이다.

```
납품업체 / 구매기업 / 채권번호 / 1억 / 지급일 / 소유자
```

중복은 완벽하게 막히지만, 애초에 A가 B에게 못 넘기던 정보를 이제 아무나 보는 곳에 올린 셈이 된다. 문제를 푸는 방식이 문제를 재생산한다.

Midnight은 공개 상태와 비공개 상태를 한 계약 안에서 다룬다. 채권 원문은 보유자 쪽에 남고 원장에는 봉인값과 지문만 올라가며, "이 지문이 발급 기관이 인증한 진짜 채권에서 나왔다"를 원문 없이 검증한다.

**과장하지 않는다.** 이더리움에 별도 ZK 스택을 붙여도 만들 수 있다. 차이는 가능·불가능이 아니라, 회로·계약·검증기가 흩어지지 않고 한 언어 안에 모이며 공개 범위를 `disclose()` 호출 지점에서 코드로 감사할 수 있다는 점이다. 금융 제품에서 이건 부수 효과가 아니라 요구사항이다.

## 10. 요약: 판단이 갈릴 때

| 상황 | 기준 |
|---|---|
| 편의를 위해 원문을 응답에 담을까 | 안 된다. §4.1 |
| 조회 API로 단순화할까 | 안 된다. §4.3 |
| nullifier에 salt를 섞을까 | 안 된다. §4.4 |
| 범위 밖 기능을 추가할까 | 안 된다. §8 |
